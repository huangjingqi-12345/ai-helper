# Px-Lite 状态机定义

> **版本:** 1.1 · **日期:** 2026-05-15
>
> 每个带有 `status` 字段的实体都有正式的状态机。本文档定义所有合法状态、转换、触发条件和守卫。
>
> **重要更新（2026-05-15）：** 内容状态机已由 PM 确认为 6 态模型，替代之前的 draft/reviewing/reviewed/published/offline/rejected 模型。

---

## 1. 内容生命周期（`ContentItem.status`）— ✅ PM 已确认

> **PM 确认（2026-05-15）：** 内容状态机（医生制作患教内容）采用以下 6 态模型。

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  需求已提交    │───►│  医生分发中    │───►│  医生制作中    │
│ requirement   │    │ distributing │    │  producing   │
│  _submitted   │    │  （中间态）    │    │              │
└──────────────┘    └──────────────┘    └──────┬───────┘
                                               │
                                               ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│    已发布     │◄───│  内部审核中    │◄───│  三方审核中    │
│  published   │    │internal_review│    │ third_party  │
│              │    │  （药企审核）   │    │_review(DX+PX)│
└──────────────┘    └──────────────┘    └──────────────┘
```

### 状态定义

| 状态 | 英文 key | 定义 | 触发条件 |
|------|---------|------|---------|
| 需求已提交 | `requirement_submitted` | 药企提交诉求，但 PX 运营还没进行诉求分发 | 药企提交诉求时自动创建 |
| 医生分发中 | `doctor_distributing` | PX 运营正在进行当前任务的分发，已确认分发策略但还没分发下去。**中间态**，分发时间可能极短 | 运营确认分发策略 |
| 医生制作中 | `doctor_producing` | 已完成内容任务分发，医生制作中 | 分发完成，任务到达医生 |
| 三方审核中 | `third_party_review` | DX 医学编辑审核、PX 运营审核**均在此节点** | 医生提交制作完成的内容 |
| 内部审核中 | `internal_review` | 药企内部审核在此节点 | DX 医学编辑 + PX 运营审核通过 |
| 已发布 | `published` | 完成所有制作流程以及审核流程，在患者端发布 | 药企审核通过 |

### 转换表

| 从 | 到 | 触发 | 谁 | 守卫 / 副作用 |
|----|----|------|-----|-------------|
| *(新建)* | `requirement_submitted` | 药企提交诉求 | 药企用户 | 创建 ContentItem + RequestTicket 记录 |
| `requirement_submitted` | `doctor_distributing` | 运营确认分发策略 | PX 运营 | 生成分发候选池 |
| `doctor_distributing` | `doctor_producing` | 分发任务派单完成 | PX 运营 / 系统 | 创建 SubTask 分配给医生；**中间态可能极短** |
| `doctor_producing` | `third_party_review` | 医生提交内容 | 医生（DX 端） | 创建 ApprovalTask，进入三方审核 |
| `third_party_review` | `doctor_producing` | 三方审核驳回（DX/PX 驳回） | DX 医学编辑 / PX 运营 | 打回至 DX 端让**医学编辑修改**，修改完成后重新提交 |
| `third_party_review` | `internal_review` | 三方审核通过（DX + PX 均通过） | DX 医学编辑 + PX 运营 | 推进到药企审核节点 |
| `internal_review` | `third_party_review` | 药企审核驳回 | 药企审核人 | 打回至 DX 端让**医学编辑修改**，修改完成后重新从三方审核开始 |
| `internal_review` | `published` | 药企审核通过 | 药企审核人 | 设置 publishedAt = now，发布到患者端 |

### 驳回策略（PM 已确认）

**所有审核节点驳回均打回至「医学编辑修改」**：
- 三方审核中（DX/PX）驳回 → 打回 DX 端医学编辑修改 → 修改完成后重新提交 → 回到三方审核中
- 内部审核中（药企）驳回 → 打回 DX 端医学编辑修改 → 修改完成后重新提交 → 回到三方审核中

### 注意事项
- 6 态是**独立存储的状态**，不是纯展示层分组
- `doctor_distributing` 是**中间态**，分发时间可能极短
- 药企用户**不能**触发审核相关的状态转换（只能在内部审核中通过/驳回）
- 不存在 `offline`（下线）和 `rejected`（驳回）作为独立持久化状态 —— 驳回会回退到 `doctor_producing`（等待医学编辑修改）

### 与审批节点的映射关系

| 内容状态 | 审批阶段 |
|---------|---------|
| 需求已提交 / 医生分发中 / 医生制作中 | 审批流之前 |
| 三方审核中 | 审批节点 N1（DX 医学编辑审核）+ N2（PX 运营审核） |
| 内部审核中 | 审批节点 N3（药企审核） |
| 已发布 | 全流程通过 |

## 2. 审批任务生命周期（`ApprovalTask`）— ✅ PM 已确认

> **PM 已确认审核流程：** 医生制作完成后 → 医学编辑审核 → [医学编辑修改] → PX运营审核 → 药企审核 → 患者端发布。
> **所有节点审核不通过均打回至「医学编辑修改」**，修改完成后继续流转。
> **驳回策略：** 仅「医学编辑修改」一种，无 `to_prev_node` 选项。

```
  ┌──────────────────────────────────────────────────────┐
  │            所有节点驳回均返回此处                         │
  ▼                                                      │
┌──────────┐  通过   ┌──────────┐  通过   ┌──────────┐  │
│  节点 0   │────────►│  节点 1   │────────►│  节点 2   │  │
│(DX医学编辑 │        │(PX运营审核)│         │ (药企审核)  │  │
│   审核)   │        │          │         │           │  │
└────┬─────┘         └────┬─────┘         └────┬─────┘  │
     │ 驳回                │ 驳回                │ 驳回   │
     │                     │                    │        │
     └─────────────────────┴────────────────────┘        │
           全部打回至「医学编辑修改」                          │
           ┌──────────────────┐                           │
           │  医学编辑修改      │                           │
           │  (DX端修改完成后   │───────────────────────────┘
           │   重新从节点0流转)  │
           └──────────────────┘

  节点 2 通过 → ┌──────────────┐
               │ 患者端发布     │
               │ (全流程通过)    │
               └──────────────┘
```

### 转换表

| 动作 | 效果 | 详情 |
|------|------|------|
| **提交** | 创建任务 | `currentIdx = 0`，`rejected = false`，`startedAt = now`，首条历史记录 action='submit' |
| **通过**（节点 N） | 推进 | `currentIdx++`，`enteredAt = now`，历史记录 action='pass' |
| **通过**（末节点/药企审核） | 完成 | `currentIdx >= flow.nodes.length` = "全流程通过"，内容状态 → `published`，发布到患者端 |
| **驳回**（任意节点） | 返回医学编辑修改 | `rejected = true`，`currentIdx = 0`，`enteredAt = now`，历史记录 action='reject'。**所有节点驳回均打回至「医学编辑修改」（即 DX 端）**，修改完成后从节点 0 继续流转 |
| **重新提交**（修改后） | 重启流程 | `rejected = false`，`currentIdx = 0`，`enteredAt = now`，新增历史记录 action='resubmit' |

### SLA 计算

```typescript
const elapsedHours = (Date.now() - new Date(task.enteredAt).getTime()) / 3600000;
const slaHours = currentNode.timeoutHours; // 通常为 8
const isOverdue = elapsedHours > slaHours;
const remainingHours = Math.max(0, slaHours - elapsedHours);
```

超时时：行高亮为红色，触发超时动作（飞书提醒 = Lark 通知）。

## 3. 项目生命周期（`Project.status`）

```
┌─────────┐    ┌───────────┐    ┌──────────────┐    ┌───────────┐    ┌──────────┐
│  intake  │───►│ producing │───►│ distributing │───►│ completed │───►│ archived │
│  (受理中) │    │  (制作中)   │    │   (分发中)    │    │  (已完成)   │    │  (已归档)  │
└─────────┘    └───────────┘    └──────────────┘    └───────────┘    └──────────┘
```

### 转换表

| 从 | 到 | 触发 | 谁 |
|----|----|------|-----|
| *(新建)* | `intake` | 项目创建（管理员或自动从诉求创建） | ops-admin |
| `intake` | `producing` | 首条内容开始制作 | 系统（自动） |
| `producing` | `distributing` | 所有内容审批通过，开始分发 | 运营 |
| `distributing` | `completed` | 分发目标达成 | 运营 |
| `completed` | `archived` | 手动归档 | ops-admin |

### 注意事项
- 演示站在分发页面显示 5 个状态桶：受理中 4、制作中 6、分发中 2、已完成 2、已归档 0
- PRD 中使用 `producing`，但演示站在分发视图中标签为"制作中"，在管理/项目视图中标签为"进行中" —— **使用 `producing` 作为 key，不同上下文展示不同标签**

## 4. 诉求生命周期（`RequestTicket.status`）

```
┌─────────┐    ┌──────────────┐    ┌───────────┐    ┌──────────────┐    ┌───────────┐
│ pending  │───►│ in_progress  │───►│ in_review │───►│ distributing │───►│ completed │
│  (待受理) │    │   (进行中)    │    │  (审核中)  │    │   (分发中)    │    │  (已完成)   │
└────┬────┘    └──────────────┘    └─────┬─────┘    └──────────────┘    └───────────┘
     │                                    │
     │                                    │ (全部驳回)
     │                                    ▼
     │                              ┌──────────┐
     └─────────────────────────────►│ rejected │
              (直接驳回)              │  (已驳回)  │
                                    └──────────┘
```

### 转换表

| 从 | 到 | 触发 | 谁 |
|----|----|------|-----|
| *(新建)* | `pending` | 药企提交诉求 | 药企用户 |
| `pending` | `in_progress` | 运营受理并开始处理 | 运营 |
| `pending` | `rejected` | 运营驳回诉求 | 运营 |
| `in_progress` | `in_review` | 内容进入审批流 | 系统 |
| `in_review` | `distributing` | 所有内容审批通过 | 系统 |
| `in_review` | `in_progress` | 内容被驳回，回到制作 | 系统 |
| `distributing` | `completed` | 分发目标达成 | 运营 |

### 关系说明（PM 已确认）
- 一个项目可以关联多个诉求（Project 1:N RequestTicket）
- 一个诉求只能关联一个项目
- 关联方向以 `RequestTicket.projectId` 为准

```
┌───────┐    ┌────────┐    ┌──────────┐
│ draft │───►│ active │◄──►│ inactive │
│ (草稿)  │    │ (已启用) │    │ (已停用) │

| 从 | 到 | 触发 | 守卫 |
|----|----|------|------|

| `inactive` | `active` | 管理员切换开关 | — |
| `draft` | `active` | 管理员激活 | 需完成签约与范围配置 |

## 6. 账号生命周期（`Account.status`）

> **PM 已确认（2026-05-15）：** 本次没有 RBAC 能力，只有两个视图。运营账号→运营视图，药企账号→药企视图。

```
┌──────────┐    ┌────────┐    ┌────────┐
│ invited  │───►│ active │◄──►│ frozen │
│ (已邀请)  │    │ (已激活) │    │ (已冻结) │
└──────────┘    └────────┘    └────────┘
```

| 从 | 到 | 触发 | 守卫 |
|----|----|------|------|
| *(通过向导新建)* | `invited` | 管理员邀请账号 | — |
| `invited` | `active` | 用户接受邀请 / 首次登录 | — |
| `active` | `frozen` | 管理员切换开关 | `invited` 状态不可冻结 |
| `frozen` | `active` | 管理员切换开关 | — |

### 账号类型（PM 已确认）
- `ops`（运营）：登录后看到运营视图
- `pharma`（药企）：登录后看到药企视图
- 无细粒度 RBAC，不实现区域/字段级权限

## 7. 子任务生命周期（`SubTask.status`）

```
┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────┐
│ assigned │───►│ drafting │───►│ reviewing │───►│ done │

| 从 | 到 | 触发 | 谁 |

| `assigned` | `drafting` | 医生接受任务 | 医生（DX） |
| `drafting` | `reviewing` | 医生提交草稿 | 医生（DX） |
| `reviewing` | `done` | 医学编辑通过 | DX 编辑 |
| `reviewing` | `drafting` | 医学编辑驳回 | DX 编辑 |

## 8. 诉求子项状态（`RequestItem.status`）

```
┌──────┐    ┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────┐
│ todo │───►│ assigned │───►│ drafting │───►│ reviewing │───►│ done │
│(待处理)│    │  (已分配)  │    │  (撰写中)  │    │  (审核中)   │    │ (完成) │
└──────┘    └──────────┘    └──────────┘    └───────────┘    └──────┘
```

每个 RequestItem 追踪一条子项（主题 + 受众 + 形式）。状态跟随 SubTask 生命周期，因为每个子项映射到一个或多个 SubTask。

## 9. 错误处理策略（PM 已确认）

> **PM 确认（2026-05-15）：** 失败后页面内显示提示文案「系统报错、请重试」，状态回滚到上一步让用户重新操作。

| 场景 | 处理方式 |
|------|---------|
| 单条操作失败（审批/发布/创建） | 后端回滚事务，状态保持不变；前端 toast 提示"系统报错、请重试" |
| 批量操作中途失败 | 已成功的保持，失败的回滚；返回部分成功结果 |
| 多步骤向导失败 | 回滚到失败步骤前的状态，用户可重试当前步骤 |
| 状态转换冲突（并发修改） | 拒绝操作，提示重试 |
