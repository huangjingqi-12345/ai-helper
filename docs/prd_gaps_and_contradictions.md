# PRD 缺口、矛盾与待决问题

> **版本:** 1.0 · **日期:** 2026-05-14
>
> 本文档梳理了三份 PM PRD 文档和演示站 px.senzco.com 之间发现的所有矛盾、歧义和缺失定义。按对工程交付的影响分优先级。
>
> **来源文档：**
> - PRD A：`Px-Lite_PRD_·_数据表结构与字段口径.pdf`（数据模型）
> - PRD B：`Px-Lite_PRD_·_运营视图.pdf`（运营视图）
> - PRD C：`Px-Lite_PRD_·_药企视图.pdf`（药企视图）
> - PRD D：`PX-三端系统交互及核心诉求.pdf`（三端系统交互）
> - 演示站：https://px.senzco.com/

## 🔴 P0 — 阻塞工程启动（编码前必须解决）

### GAP-001：内容状态枚举矛盾

| 来源 | 定义的状态 |
|------|----------|
| PRD A §1.1 ContentItem.status | `draft`、`published`、`offline`（3 态） |
| PRD B §2.3 内容工坊筛选 | `draft`、`审核中`、`已上线`、`已下线`、`已驳回`（5 态） |
| PRD B 附录 C | `draft`、`reviewing`、`reviewed`、`published`、`offline`、`rejected`（6 态） |
| 演示站内容工坊 | 显示 6 个流水线桶 + 草稿/审核中/已发布等状态标签 |

**影响：** Schema 设计、所有状态相关查询、审批流集成、UI 筛选选项。

**建议：** 使用 PRD B 附录 C 的 6 态模型。PRD A 的 3 态模型看起来是更早期/简化的版本。

**❓ 需要 PM 决策：** 确认 6 态模型。`reviewed`（审核通过）是一个真实持久化的状态，还是仅仅是运营点击"发布"前的瞬间过渡？

---

### GAP-002：工坊 6 桶 与 审批 3 节点不匹配

| 来源 | 模型 |
|------|------|
| PRD A §1.2 WorkshopExtra.flowStatus | 6 桶：需求已提交 / 医生分发中 / 医生制作中 / 三方审核中 / 内部审核中 / 已发布 |
| PRD A §4.1-4.4 审批模型 | 3 节点流程：DX医学审核 → PX运营审核 → 药企审核 |
| 演示站内容工坊 | 顶部显示 6 桶 |
| 演示站审批流配置 | 显示 3 个节点 |

**影响：** 6 桶覆盖的生命周期远比 3 节点审批流更广。桶 1-3（需求已提交、医生分发中、医生制作中）发生在任何审批节点之前。这两个模型之间的关系从未被明确定义。

**❓ 需要 PM 决策：**
1. 6 桶是纯展示层的分组（从其他字段派生）？还是独立存储的状态？
2. "三方审核中"如何映射到审批节点？是 N3（药企审核）还是其他？
3. "内部审核中" = N1（DX）+ N2（PX）？还是仅 N2？

---

### GAP-003：Project ↔ RequestTicket 关系歧义

| 来源 | 关系 |
|------|------|
| PRD A §3 引言 | "四级层次：Project 1:N RequestTicket 1:N RequestItem 1:N SubTask" |
| PRD A §3.1 Project.ticketId | `ticketId: string?` — "项目关联的首条药企诉求"（暗示 1:1 或 1:首条） |
| PRD B §4.4 项目详情 | 显示"关联诉求列表"（一个列表，暗示 1:N） |
| 演示站分发策略 | 显示项目带有多条诉求（如"诉求 3条"） |

**影响：** 数据库 Schema 设计。如果是 1:N，`Project.ticketId` 就没有意义。如果是 1:1，演示站的"诉求 3条"就没有意义。

**❓ 需要 PM 决策：** `Project.ticketId` 是否是应该移除的遗留字段？Project 应该有 `requestTicketIds: string[]` 还是应该依赖 `RequestTicket.projectId` 作为关联方向？

---

### GAP-004：三端系统集成接口未定义

| 缺失项 | 影响 |
|--------|------|
| DX → PX 回调 API 格式 | 无法实现 DX 任务同步 |
| CX → PX 行为数据 API 格式 | 无法实现真实分析 |
| 系统间鉴权 | 安全审查受阻 |
| 同步机制（webhook/轮询/批量） | 架构决策受阻 |
| 错误处理与重试策略 | 可靠性设计受阻 |

PRD D 只描述了 PX 需要从 DX/CX 获取**什么数据**，从未定义**如何传递**。整份文档是一个需求愿望清单，缺乏接口契约。

**❓ 需要 PM 决策：** DX/CX 集成是否在 v1 范围内？如果是，需要 DX 和 CX 团队提供接口契约。如果不是，需要记录 mock 数据策略。

---

### GAP-005：AIGC 内容生成流程未定义

PRD B §8.1 提到"AIGC 4步生成"并列出枚举（AIGC_CONTENT_TYPES、AIGC_FORMATS、AIGC_TONES、AIGC_LENGTHS），但是：

| 缺失项 | 详情 |
|--------|------|
| 步骤流程 | 4 步是什么？用户在每一步看到/输入什么？ |
| AI 服务集成 | AIGC 调用什么 API？提示词结构是什么？ |
| 输出格式 | AIGC 返回什么？Markdown？HTML？结构化 JSON？ |
| 草稿创建 | AIGC 输出如何变成 ContentItem？ |
| 错误处理 | 如果生成失败怎么办？超时？ |

**❓ 需要 PM 决策：** 完整的 AIGC 向导规格。这是 v1 功能还是仅演示？

## 🟡 P1 — 阻塞并行开发（功能完成前必须解决）

### GAP-006：KPI 计算"互动数"口径不一致

| 来源 | 公式 |
|------|------|
| PRD A §1.1 关键说明 | `互动数 = likes + favorites`（平台统一口径） |
| PRD A §1.1 第二条说明 | "Overview.tsx 与 ContentDetail.tsx 仍保留 +dislikes 的历史口径" |
| PRD B §3.2 行为 KPI | `Σ(likes + collects) / Σ(views) × 100%` 计算"平均互动率" |
| 演示站内容详情 | 显示"赞 373 · 踩 26 · 藏 286" — 包含踩数展示 |

**❓ 需要 PM 决策：** 互动数的最终公式。`dislikes` 是否应包含在计数中？应该展示但不计入？PRD 说"后续将统一收敛到 likes+favorites" — "后续"是现在吗？

---

### GAP-007："阅读人数"近似值 — 这是真实数据吗？

PRD A 定义：`阅读人数 ≈ floor(reads × 0.78)`

这是一个**硬编码的近似值**，却伪装成真实指标。演示站将其与真实指标并列展示为精确数字。

**❓ 需要 PM 决策：**
1. 这在生产环境可接受吗？还是需要 CX 提供真实 UV 追踪？
2. 如果保留近似值，UI 是否应标注这是估算值？
3. 0.78 系数是可配置的还是固定的？

---

### GAP-008：`favorites` vs `collects` 命名

| 来源 | 使用的术语 |
|------|----------|
| PRD A §1.1 ContentItem 字段 | `favorites`（字段名） |
| PRD B §2.3 模块 A KPI | "Σlikes+collects" |
| PRD B §3.2 行为 KPI | "Σ(likes+collects)/Σ(views)" |
| PRD C §1.2 药企 KPI | "Σlikes+collects" |

**影响：** 代码必须统一使用一个名称。PRD A 用 `favorites` 作为字段名，但 PRD B/C 在公式中用 `collects`。

**建议：** 使用 `favorites` 作为字段名（与 PRD A 数据模型一致）。展示标签 = "收藏"。

---

### GAP-009：缺少状态转换规则

PRD 列出了状态枚举但从未定义合法转换。具体：

| 实体 | 缺失项 |
|------|--------|
| ContentItem | `offline` → `published`（重新发布）是否合法？`rejected` → `draft` 还是直接到 `reviewing`？ |
| RequestTicket | 部分驳回时 `in_review` → `in_progress` 是否合法？ |
| Project | 状态是从内容/诉求状态自动派生的，还是手动设置的？ |
| SubTask | `reviewing` → `drafting`（编辑驳回回医生）是否合法？ |

**❓ 需要 PM 决策：** 每个实体的完整状态转换规则。请查阅我们的 `state_machines.md` 中提出的规则 — 请确认或修正。

### GAP-011：演示功能 vs 生产功能

PRD 中频繁出现"demo保留"/"UI已下线"/"兼容字段"，但未明确说明什么在 v1 范围内、什么不在。示例：

| 项目 | PRD 说法 | 问题 |
|------|---------|------|
| 字段权限矩阵（FIELD_KEYS） | "UI已下线，数据保留" | 是否构建后端执行？ |
| DoctorPolicy.departments/regions/tags | "UI已下线，仅保留titles" | Schema 中删除？保留为 nullable？ |
| DistributeStrategy.ramp | "灰度比例UI已下线" | 删除？ |
| Tenant.scope.rampUpperBound/exportEnabled/kAnonymity | "UI全部隐藏；mock字段保留" | 实现后端执行？ |
| 财务模块 | "ENABLE_FINANCE_MENU=false" | 构建后端表？API 端点？ |
| Project.priority / expectGoLive | "新建对话框已下线该入口" | 但演示站显示优先级标签（P0/P1）。哪个是对的？ |

**❓ 需要 PM 决策：** 明确的"v1 范围"文档，列出每个功能为 纳入/排除/延后。

## 🟢 P2 — QA/上线前应解决

### GAP-012：内容工坊 — PRD B 说 5 张 KPI 卡片，但演示站显示 6 桶流水线 + 不同布局

PRD B §2.3 模块 A 描述"顶部KPI（5张卡）"：累计内容、已上线、审核中、已下线、患者总互动。

但演示站显示的是 6 状态桶的流水线视图（需求已提交、医生分发中等）— 没有传统的 KPI 卡片。

**❓ 需要 PM 决策：** 哪个布局是正确的？演示站的流水线视图还是 PRD 的 5 张 KPI 卡片？

### GAP-013：总览页面布局不匹配

| PRD B §1.2 描述 | 演示站显示 |
|----------------|----------|
| 4 张 KPI 卡片（待我审批、制作中诉求、本周新发布、患者总互动） | 6 张 KPI 卡片（项目数、已发布内容、推送人数、阅读人数、阅读次数、互动数） |

**❓ 需要 PM 决策：** 演示站的简化布局是目标？还是应该构建 PRD B 描述的完整布局（含收件箱 + 图表）？

### GAP-014：行为洞察页面 — PRD vs 演示站不匹配

演示站的行为洞察页面明显更简化 — 只有 KPI 卡片 + TopN 列表。PRD 描述了人口画像、趋势图表等。

PRD A 定义了 `ContentItem.channelBreakdown: Record<Channel, number>`（触达次数按渠道拆解），但 PRD B 或 PRD C 中没有任何 UI 引用过此数据的展示。

**❓ 需要 PM 决策：** 渠道分布 UI 是否不在范围内？是否仍需存储该字段？

### GAP-017：患者表 — Mock vs 真实

PRD A §2.1 说所有患者真实姓名/手机号"从前端 mock 中全部剔除"，FIELD_KEYS 中仍保留 `patient.realName`、`patient.phone` 作为"字段口径占位"。

两份视图 PRD 中的行为洞察页面从不显示单个患者行 — 只有聚合数据。

**❓ 需要 PM 决策：**
1. 运营视图中是否有患者级别的下钻？
2. `route:patients` 能力存在但没有任何 PRD 描述 `/patients` 页面。这是做什么用的？

---

### GAP-018：PRD D（三端系统文档）质量问题

三端系统文档（`PX-三端系统交互及核心诉求.pdf`）存在显著问题：

1. **第一节为空** — 只有标题"医生任务分发及患者端展示系统流程"，没有内容
2. **没有接口定义** — 只描述"我们想要什么"而非"如何获取"
3. **"支持节奏"列为空** — 没有时间承诺
4. **混淆 PX 关注点与 DX/CX 关注点** — 文档要求 DX 支持功能但未定义契约

这份文档本质上是功能愿望清单，不是技术规格。

**建议：** 应由 DX 和 CX 团队共同编写一份正式的集成规格来替代此文档。

---

### GAP-019：租户切换器 — 与侧边栏说明矛盾

演示站侧边栏显示"说明"面板，写着"运营视图 Ops View，合规枢纽，唯一可见患者明文，全部生产/触达能力"。但演示站中实际的运营用户是"系统管理员 · 华东区域 · admin" — 暗示有区域范围限制，不是"全部"。

**❓ 需要 PM 决策：** 是否存在区域范围的运营账号？RBAC 矩阵中未提及基于区域的访问控制。

---

### GAP-020：缺少错误处理规格

没有任何 PRD 定义了操作出错时的处理方式：
- 批量审批中途失败怎么办？
- 发布失败（如内容已被修改）怎么办？
- 租户创建在第 3 步（共 4 步）失败怎么办？
- 分发派单部分失败怎么办？

**建议：** 为每个关键操作添加错误处理需求，或至少定义重试/回滚策略。
