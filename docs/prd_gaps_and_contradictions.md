## 🔴 P0 — 阻塞工程启动（编码前必须解决）

### GAP-001：内容状态枚举矛盾 — ✅ 已解决

| 来源 | 定义的状态 |
|------|----------|
| PRD A §1.1 ContentItem.status | `draft`、`published`、`offline`（3 态） |
| PRD B §2.3 内容工坊筛选 | `draft`、`审核中`、`已上线`、`已下线`、`已驳回`（5 态） |
| PRD B 附录 C | `draft`、`reviewing`、`reviewed`、`published`、`offline`、`rejected`（6 态） |
| 演示站内容工坊 | 显示 6 个流水线桶 + 草稿/审核中/已发布等状态标签 |

**影响：** Schema 设计、所有状态相关查询、审批流集成、UI 筛选选项。

**✅ PM 已确认（2026-05-15）：** 内容状态机（医生制作患教内容）采用以下 6 态模型：

| 状态名称 | 状态定义 |
|---------|---------|
| 需求已提交 | 药企提交诉求，但 PX 运营还没进行诉求分发 |
| 医生分发中 | PX 运营正在进行当前任务的分发，已确认分发策略但还没分发下去。因为分发时间可能极短所以是**中间态** |
| 医生制作中 | 已完成内容任务分发，医生制作中 |
| 三方审核中 | DX 医学编辑审核、PX 运营审核均在此节点 |
| 内部审核中 | 药企内部审核在此节点 |
| 已发布 | 完成所有制作流程以及审核流程，在患者端发布 |

**工程影响：** 废弃 PRD A 的 3 态和 PRD B 附录 C 的 `draft/reviewing/reviewed/published/offline/rejected` 模型。Schema 使用上述 6 态作为 `ContentItem.status` 枚举。详见 `state_machines.md`。

### GAP-002：工坊 6 桶 与 审批 3 节点不匹配 — ✅ 已解决

| 来源 | 模型 |
|------|------|
| PRD A §1.2 WorkshopExtra.flowStatus | 6 桶：需求已提交 / 医生分发中 / 医生制作中 / 三方审核中 / 内部审核中 / 已发布 |
| PRD A §4.1-4.4 审批模型 | 3 节点流程：DX医学审核 → PX运营审核 → 药企审核 |
| 演示站内容工坊 | 顶部显示 6 桶 |
| 演示站审批流配置 | 显示 3 个节点 |

**✅ PM 已确认（2026-05-15）：**

1. **6 桶是独立存储的状态**，参考 GAP-001 确认的内容状态机，不是纯展示层分组。
2. **三方审核中** = DX 医学编辑审核 + PX 运营审核（均在此节点完成）
3. **内部审核中** = 药企内部审核在此节点

**工程理解：** 6 态即内容主状态，映射关系为：
- 需求已提交 / 医生分发中 / 医生制作中 = 审批流之前的阶段
- 三方审核中 = 审批节点 N1（DX 医学编辑审核）+ N2（PX 运营审核）
- 内部审核中 = 审批节点 N3（药企审核）
- 已发布 = 全流程通过并发布

### GAP-003：Project ↔ RequestTicket 关系歧义 — ✅ 已解决

| 来源 | 关系 |

**工程决策：** 确认 1:N 关系。移除 `Project.ticketId`，查询时通过 `RequestTicket.projectId` 反查。

### GAP-006：KPI 计算"互动数"口径不一致 — ✅ 已解决

| 来源 | 公式 |
|------|------|
| PRD A §1.1 关键说明 | `互动数 = likes + favorites`（平台统一口径） |
| PRD A §1.1 第二条说明 | "Overview.tsx 与 ContentDetail.tsx 仍保留 +dislikes 的历史口径" |
| PRD B §3.2 行为 KPI | `Σ(likes + collects) / Σ(views) × 100%` 计算"平均互动率" |
| 演示站内容详情 | 显示"赞 373 · 踩 26 · 藏 286" — 包含踩数展示 |

**✅ PM 已确认（2026-05-15）：**
- **策略分发以及端内其他互动数指标展示均为正向互动数**
- **互动数（正向） = 点赞 + 收藏**
- **患教内容互动数**：当前患教内容的正向互动数量（点赞 + 收藏）
- **医生互动数**：此医生已制作完成的所有文章的正向互动数总和

**工程行动项：**
1. 统一互动数公式为 `likes + favorites`，移除 `dislikes` 参与计算
2. `dislikes` 字段可保留存储，但**不计入**互动数指标
3. UI 展示互动数时使用"正向互动数"标签
4. 医生维度互动数 = `SUM(likes + favorites)` across all published content by that doctor

### GAP-007："阅读人数"近似值 — ✅ 已解决

PRD A 定义：`阅读人数 ≈ floor(reads × 0.78)`

这是一个**硬编码的近似值**，却伪装成真实指标。演示站将其与真实指标并列展示为精确数字。

**✅ PM 已确认（2026-05-15）：**
1. 需要读取患者端**真实数据**，本期可暂时使用虚拟数据
2. 数据是**真实的自然整数**，不是估算值
3. **不应该有 0.78 系数** — 移除该近似算法

**工程行动项：**
1. 移除 `floor(reads × 0.78)` 近似算法
2. `read_users` 作为独立字段，从患者端（CX）真实数据导入
3. 本期 CX 未对接前，使用虚拟数据占位（需在代码中标注为 mock）
4. UI 不需要标注"估算值"，因为生产数据应为真实值

### GAP-020：缺少错误处理规格 — ✅ 已解决

没有任何 PRD 定义了操作出错时的处理方式：
- 批量审批中途失败怎么办？
- 发布失败（如内容已被修改）怎么办？
- 租户创建在第 3 步（共 4 步）失败怎么办？
- 分发派单部分失败怎么办？

**✅ PM 已确认（2026-05-15）：**
- 失败后页面内显示提示文案 **「系统报错、请重试」**
- **状态回滚到上一步**，让用户重新操作

**工程决策：**
1. 所有关键操作（审批、发布、创建、分发）失败时：
   - 后端回滚事务，保持状态不变（即"回滚到上一步"）
   - 前端显示 toast/提示："系统报错、请重试"
2. 批量操作中途失败：已成功的保持，失败的回滚，返回部分成功结果
3. 多步骤向导失败：回滚到失败步骤前的状态
